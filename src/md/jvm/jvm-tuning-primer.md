> 整理自一段集中啃 JVM 的日子：指令手册翻过一轮、调优工具挨个用过，最后在生产上实战了一次。这篇是提纯后的主干——参数怎么选、工具怎么用、实战怎么打。

## 一、参数体系：记住三块内存就够

JVM 参数万万千千，先建立"三块内存"的心智模型：

| 区域 | 关键参数 | 一句话 |
|---|---|---|
| 堆 | `-Xms` / `-Xmx`（建议相等，免得动态伸缩抖动） | 对象的家 |
| 非堆/元空间 | `-XX:MetaspaceSize` / `MaxMetaspaceSize` | 类元数据（1.8 起取代 PermSize） |
| 栈 | `-Xss` | 每线程独立一份——**线程数 × Xss = 栈总预算**（泄漏类问题的账要这么算） |

GC 器选型（当年视角）：G1 已是大堆默认答案（`-XX:+UseG1GC` + `MaxGCPauseMillis` 定目标暂停），CMS 只在历史项目里见到。

## 二、工具链：按"离线→在线"排个序

1. **jps / jinfo**：确认进程、查参数（`jinfo -flags <pid>` 看实际生效值，比配置文件诚实）；
2. **jstat**：`-gcutil <pid> 1000` 每秒采样——**GC 频率、各代占用趋势**是调优的核心观测面；
3. **jmap**：堆转储（`-dump:live,format=b,file=heap.hprof`）——喂给 MAT 分析 dominator tree；
4. **jstack**：线程快照——查死锁、看线程数、定位线程状态分布；
5. **GC 日志**：`-Xlog:gc*`（1.9+）长期开着，线上问题的第一现场。

口诀：**先 jstat 看趋势，再 jmap 拿证据，jstack 管线程，GC 日志管长线**。

## 三、实战：扩堆的四步纪律

一次生产割接 OOM 的处理（详见数据割接篇）：本地脚本正常、生产 800 万行时 OOM。

当时的处置四步，值得复用：

1. **分清 OOM 种类**：`heap space`（堆）/ `Metaspace`（类加载）/ `unable to create new native thread`（线程）——方向完全不同；
2. **看数据形态**：脚本内累积结构随数据量线性增长 → 堆需求确实随进度上涨；
3. **止血**：堆从 2G 扩到 8G（内存充裕的前提下，快速让业务先跑通）；
4. **记账**：扩参数是止血不是治疗——累积式内存形态的根治是改成流式处理，记入技术债。

## 复盘

JVM 调优的一半是知识（参数语义、GC 器行为），另一半是纪律（先观测再动手、止血与根治分开、每次调整留档）。参数可以背，纪律得练。
