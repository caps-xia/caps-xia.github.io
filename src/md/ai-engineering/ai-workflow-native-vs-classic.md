> 你有没有过这种经历：让 AI 写一个功能，第一版很惊艳；然后产品说"这里改一下"、你说"那个方案不对"、隔天又推翻重来——三轮之后，AI 交付的东西和最初的需求已经对不上了，代码和文档成了两张皮，你也说不清"到底做完没做完"。

这不是模型不行，是**缺少一个把"需求、验收标准、进度、结论"钉死的工作流**。

最近我用团队在用的 AI 编码流程治理工具 **Comet**（一个架在 Claude Code 等 Agent 之上的工作流层），完整走了一个中等规模的真实需求：两张新表、若干新接口、横跨管理后台和 C 端两个服务，中途**需求改了 7 轮**。这篇文章就把 Comet 的几种工作流模式掰开讲清楚——工作过程、每阶段产物、怎么选，以及我在实战里踩过的坑。

---

## 一、先看全景：Comet 有几套工作流？

```
Comet（.comet/config.yaml 的 workflows 决定启用谁）
│
├── Native  ──── Shape → Build ↔ Verify → Archive        （自适应：锁结果与证据，不锁方法）
│
└── Classic ──── 三个档位（preset）
    ├── full    ── open → design → build → verify → archive（完整五阶段）
    ├── hotfix  ── open → build → verify → archive（跳过 design，修 bug 用）
    └── tweak   ── open → build → verify → archive（跳过 design，小调整用）
```

三条铁律：

0. **一个项目只启用一套**（Native 或 Classic，由 `.comet/config.yaml` 决定）；
1. **一个需求只能由一个 workflow/change 管理**，不能两套混用；
2. Classic 的档位创建时确定，只能**单向升级**（轻量档 → full），不能降级。

如果只记一句话选型口诀：

> **改的是错的东西 → hotfix；改对的东西但不扩大范围 → tweak；新增能力、动结构 → full。** 项目启用 Native 时不用纠结，一律 Native。

## 二、Native：锁结果与证据，不锁方法

### 2.1 核心理念

Native 的哲学是：把**需求、完整目标规格、当前进度、验收结论**全部沉淀为项目里的正式文件；一个叫 **Runtime** 的命令行（`comet native`）管理所有状态、检查执行和轮次预算；Agent（也就是 AI）每个时刻只做 Runtime 指定的当前阶段。

它**不管你怎么实现**——不强制你先写设计文档、不强制 TDD、不规定任务拆分方式，只锁两样东西：**验收项是否全部通过**、**每个结论是否有证据**。文档里的说法是"适合 Fable 5 / GPT-5.6 档的强模型"——模型越强，过程约束越应该让位于结果约束。

### 2.2 四个阶段与产物

```
Shape ──确认──▶ Build ──交接──▶ Verify ──通过──▶ Archive
  ▲                                  │失败
  └──── 需求修订 ────────────────────┘──回 Build──▶ 修复重验
```

| 阶段 | 干什么 | 关键动作 | 落什么产物 |
| --- | --- | --- | --- |
| **Shape** | 把需求变成"可验收的目标" | AI 先调查代码库事实 → 把真正需要**人拍板**的决策（会改变用户可见结果的）拎出来问你 → 生成验收清单 | `brief.md`（目标/范围/非目标/验收项/决策记录）、`specs/<能力>/spec.md`——注意这是**完整目标规格**，写的是"这个功能做完后应该是什么行为"，不是变更增量 |
| **Build** | 实现 + 自查 | 写代码、跑编译测试，然后提交一份 **Builder 交接摘要**：这轮做了什么、覆盖了哪些验收项、跑了什么检查、还有什么已知限制 | 代码改动 + 状态文件里的 handoff |
| **Verify** | **独立**验收 | Runtime 先跑客观检查（编译/单测/DDL 核对……），然后派一个**全新的、只读的 Verifier 子 Agent**——它没参与实现，逐条验收项给 passed/failed/blocked | `verification.md` 验收报告 |
| **Archive** | 归档交付 | 你确认后归档产物、选择分支收尾方式（merge / push / PR / 保留） | 归档目录 + 唯一归档提交 |

两个设计点值得细品：

* **Builder 不能自证完成**。你提交的只是"候选"，不是"完成的证明"——必须由一个没写过这坨代码的新 Agent 独立验收。这从机制上消灭了"AI 说做完了但其实没做完"。
* **验收项一个都不能漏**。Verifier 必须对每个验收 ID 恰好给出一次结论，漏项、重复、未知 ID 都会被 Runtime 直接拒收。

### 2.3 需求中途变了怎么办？（重点来了）

这是我最推荐 Native 的场景。需求变更走两条路：

* **只是实现有遗漏** → 回 Build 修完重新提验收；
* **需求本身变了**（用户可见行为/验收标准变化）→ 先修订 brief 和规格、**重新确认 Shape**、再进 Build——旧验收结论自动作废，全部重验。

我那个真实需求的时间线长这样：

```
创建 change（绑定既有分支，工作区不搬家）
→ Shape：调查 + 4 个关键决策找我确认 → brief/spec → 我确认
→ Build：实现 → 交接
→ Verify：首轮验收 52 项全过 → 我在确认时说"门店校验口径不对，改"
→ (循环 × 7 轮)：
    "和商品相同的配置干脆别存了"      → 撤回重做 + 重新确认 + 重验收
    "第三张打标表不要了，查开关就行"   → 删表删代码 + 重确认 + 重验收
    "单个合作方也应该能配"           → 删校验 + 重验收
    "对照表接口参数太多了"           → 简化入参 + 重验收
    "没配置就别抛异常，前端体验差"     → 柔性降级 + 重验收
    ……
→ 最终 57 项验收全过 → 按我的要求停在归档前，代码留给我自己提交
```

7 轮变更，每一轮都有产物留痕、验收重跑、旧结论作废。事后翻 `docs/comet/changes/<name>/` 目录，需求是怎么一步步演进到今天这个样子的，全程可追溯——**这是普通"AI 直接写代码"模式永远给不了的东西**。

### 2.4 有界的验收循环

防止 AI 和 Verifier 无限互相拉扯：`iteration`（实现候选轮次）、`attempt`（同一候选的验收次数）都有预算，比如验收最多失败 5 次、执行错误最多 3 次，耗尽就阻塞等你来拍板，不会烧着 token 死循环。

## 三、Classic：锁过程的五阶段流水线

Classic 是更传统的阶段制，配合 OpenSpec（规格产物）+ Superpowers（过程技能库），每一阶段有**硬门禁**（guard 脚本校验产物完备性，不过不放行），阶段推进只能走 `comet-guard <name> <phase> --apply`，禁止手改状态文件。

### 3.1 五阶段骨架（full 的完整形态）

| 阶段 | 职责 | 必须由人拍板的停顿点 | 产物 |
| --- | --- | --- | --- |
| **open** | 想法 → 变更提案：反复澄清需求后逐个生成产物（**禁止一次性生成**） | 大 PRD 拆不拆、工作区隔离方式（当前分支/新分支/worktree）、产物审视 | `proposal.md`（目标/动机/范围）、`design.md`（高层架构）、`tasks.md`（任务清单）、delta spec（变更增量规格）、状态文件 |
| **design** | 深度设计 | 头脑风暴方案确认 | **Design Doc** + handoff 交接包（脚本生成、带 sha256，**禁止手写摘要**） |
| **build** | 执行实现 | plan 就绪后**一次联合四选**：工作区隔离 / 执行方式 / TDD 模式 / 审查模式 | 实现计划、`tasks.md` 打勾、逐任务 commit |
| **verify** | 验证 | 失败处理策略；连败 3 次选"接受偏差"还是"继续修" | 验证报告（按 CRITICAL/MAJOR/MINOR 分级） |
| **archive** | 归档交付 | 五选：仅本地归档 / 归档+推送 / 归档+推送+建 PR / 回 verify 重验 / 暂不归档 | delta spec 合并进主规格、change 移入归档目录、唯一归档提交 |

### 3.2 三个档位到底差在哪

| 维度 | **full** | **hotfix** | **tweak** |
| --- | --- | --- | --- |
| 目标 | 新功能 / 架构 / 大需求 | 修 bug | 调整行为或内容 |
| 流程 | open→**design**→build→verify→archive | open→build→verify→archive | 同 hotfix |
| Design Doc | 必需 | 合法跳过 | 合法跳过 |
| proposal 内容 | 目标/动机/范围 + 方案对比 | 问题 + **根因分析** + 修复目标（单方案） | 动机 + 目标 + 范围 |
| delta spec | 按 PRD 拆分 | **例外**（仅当修复改变了已有验收场景） | **正式产物**（需要改 spec 本身不构成升级理由） |
| build 方式 | 写计划 + 四选（可 subagent/TDD） | 手动逐任务修复 | OpenSpec apply 路径（tweak 专属） |
| 根因消除检查 | — | **有**（hotfix 专属，防止只压症状） | — |
| 代码审查默认档 | standard | off | off |
| 默认分支 | 按项目 | `hotfix/YYYYMMDD/<name>` | `tweak/YYYYMMDD/<name>` |
| commit 前缀 | 按规范 | `fix:` | `tweak:` |
| 文件数绊线 | — | 超过 4 个触发升级评估 | 超过 6 个 |

两个最容易混淆的点，官方文档专门强调过：

0. **tweak 和 hotfix 的本质区别是 delta spec 的地位**——hotfix 把"改规格"当例外，tweak 把它当正常产物。你的变更天然需要修改既有规格？那 tweak 就是对的，不因此升级。
1. **build 执行路径不同**——tweak 走 OpenSpec 原生 apply 路径，这条路径只属于 tweak，full 不得套用。

### 3.3 单向升级机制

hotfix/tweak 执行中如果命中**质变信号**——跨模块协调、新对外 API、数据库 schema 变更、深层架构问题——或者文件数超绊线，Comet 会停下来让你二选一：继续轻量流程，或升级为 full。升级只有一条合法通道：

```
comet state transition <name> preset-escalate
# 效果：档位置为 full，阶段回退到 design，清空 design_doc，补完整设计后再继续
```

注意 full **没有** build→design 的回退通道：full 执行中发现设计问题，是在 build 阶段原地用头脑风暴更新 Design Doc 解决（改动分小/中/大三级处理），只有"全新能力"才开新 change。

### 3.4 代码审查强度（review\_mode）

| 模式 | 任务级审查 | 适用 |
| --- | --- | --- |
| `off` | 无 | hotfix/tweak、低风险小改（默认） |
| `standard` | 仅风险任务即时审 | 日常 full（默认） |
| `thorough` | **每个任务**都审，最多 2 轮修复+复审 | 安全/认证/数据迁移/跨模块/架构 |

## 四、Native vs Classic：怎么选？

| 维度 | Native | Classic |
| --- | --- | --- |
| 哲学 | 锁结果与证据，方法自适应 | 锁过程：阶段门禁 + 产物完备性硬校验 |
| 规格形态 | **完整目标规格**（做完后的全部行为） | delta spec（本次变更的增量） |
| 验收方式 | 客观检查 + **独立只读 Verifier 逐项验收** | verify 阶段验证 + 按档位的代码审查 |
| 状态管理 | Runtime 全自动 | 脚本门禁推进 |
| 需求中途变更 | 回 Build / 修订重确认，循环天然支持 | 分级处理；轻量档可升级 full |
| 依赖外部技能 | 无 | OpenSpec + Superpowers |
| 适合 | 强模型、重证据链、**需求会反复变** | 团队要统一过程治理、要 Design Doc 留痕、需要更强过程约束 |

我的实操体感：**需求会反复改的，选 Native**——每轮变更都是"修订产物 → 重新确认 → 全量重验收"的闭环，永远不会出现文档和代码两张皮；如果团队多人协作、要审设计文档存档、模型能力一般需要过程扶着走，选 Classic。

## 五、实战踩坑记录（文档里不会告诉你的）

这部分是我在真实需求里用血泪换来的，发布前特意翻了一遍执行日志确认：

**1. 检查计划的 argv 是 spawn 风格，不含可执行文件本身**

给 Runtime 提交检查计划（dispatch-verifier）时，`argv` 数组里**不要**重复写 executable：

```
// ❌ 错：./mvnw 会被当成 Maven 的 phase，报 Unknown lifecycle phase
{"executable": "./mvnw", "argv": ["./mvnw", "compile", "-q"]}
​
// ✅ 对
{"executable": "./mvnw", "argv": ["compile", "-q", "-DskipTests"]}
```

我就因为这个，一轮检查全挂、被迫整轮重开验证。

**2. 失败的检查不能原地覆盖**

检查计划一旦被 Runtime 接受就锁定了，改了 argv 想重跑？同 ID 会被拒（conflict）。正确姿势：要么让 Verifier 通过 `request-checks` 请求等价新检查，要么退回 Build 重开一轮验证。

**3. Verifier 结果的 JSON 校验非常严格**

* 每个验收 ID **恰好出现一次**——我提交时手滑漏了一项，直接被判无效还扣了一次执行错误额度（3 次封顶）；
* `risks` 数组必须是**纯文本**，写成对象会被拒；
* `iteration`/`attempt` 必须和 Runtime 当前状态完全一致。

**4. 改了代码必须重验，没有侥幸**

Verify 阶段哪怕只改一行注释，候选指纹就变了，旧验收结论自动作废——老实回 Build 走完整循环。听起来繁琐，但这正是"验收结论永远对应磁盘上那份代码"的保证。

**5. 跨仓库需求 = 各自一个 change**

需求横跨两个服务时，别想着用一个 change 管俩仓库——每个仓库建自己的 change，靠规格里的"消费契约"章节对齐（A 仓库的规格写清楚"B 侧按什么约定读我的表"）。

## 六、一页总结

* **Native** = Shape（要什么+怎么算完）→ Build ↔ Verify（独立验收）→ Archive；Runtime 管状态，需求变更走循环重验收；产物是 brief + 完整规格 + 验收矩阵。
* **Classic full** = open（提案）→ design（Design Doc）→ build（计划+执行）→ verify → archive，硬门禁推进。
* **hotfix** = 修 bug 的轻量档（带根因消除检查，≤4 文件）；**tweak** = 小调整的轻量档（delta spec 是正式产物，≤6 文件）；命中质变信号走 `preset-escalate` 单向升级 full。
* 选型一句话：项目配置定 Native/Classic；Classic 内部按"改错的→hotfix，小改→tweak，加能力→full"；拿不准就走轻量档，升级有闸门兜底。

用了这一整套下来，最大的感受是：**AI 编码的瓶颈早就不是"写代码"了，而是"需求怎么钉死、做完怎么证明"** 。工作流层解决的就是后两件事。
