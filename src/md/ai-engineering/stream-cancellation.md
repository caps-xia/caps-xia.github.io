> 一次线上排查：SSE 客户端超时断开后，后台日志显示模型又跑了 3 分多钟——工具轮照常执行、token 照常计费，而消费者早已消失。这篇拆解这个问题在 ADK Java 里的根因、为什么框架层和应用层各需要一套方案、以及两套方案如何组合成完整防线。

## 问题：断开 ≠ 取消

流式对话的直觉假设是"客户端走了，服务端就停"。但实际链路上，"用户断开"只是一个 TCP 事件，它要变成"模型停止生成"，需要**取消信号沿着整条响应式链路逆向传播**——而这条传播路径在任何一环都可能断。

断掉的后果按严重度排：

1. **token 空烧**：模型生成到自然结束，全程计费，无消费者；
2. **工具照常执行**：模型断开后吐出的工具调用**依然会被执行**——查询生产库、调内部接口，这些副作用不再服务任何人；
3. **僵尸续流**：多轮工具循环里，"工具执行完 → 续流下一轮"的窗口若没有取消检查，新一轮订阅无人取消，越滚越远。

## 根因：cache() 的取消语义

ADK Java 的 `BaseLlmFlow` 里，每一步的事件流被这样处理：

```java
Flowable<Event> currentStepEvents = runOneStep(ctx).cache();
```

`cache()` 是为了重放（让框架内部多个消费方共享一次模型调用）。但它的取消语义是：**只有所有订阅者都取消，上游连接才会 dispose**。框架内部自己挂的订阅者（事件聚合、持久化）始终活着，于是用户侧的 dispose 永远传不到模型流。更精确地说：`FlowableCache` 根本没有取消上游的通路——它的 `cancel()` 只是把订阅者从重放列表里摘掉。

这不是我推理出来的，是生产证据 + 字节码分析的结论：断开后日志显示步骤以**零订阅者**状态继续跑完；上游 [#1618](https://github.com/google/adk-java/issues/1618) 的另一位贡献者用 `Flowable.never().doOnCancel(...)` 做了同样的实证（doOnCancel 永不触发）。

## 框架层修复：#1621 的 takeUntil 方案

社区贡献者 sangkyoonnam 的修复保留了 `cache()`（重放能力不能丢），在它前面加了一把闸：

```java
CompletableSubject cancelled = CompletableSubject.create();
return step.takeUntil(cancelled.toFlowable()).cache().doOnCancel(cancelled::onComplete);
```

下游任一订阅者取消 → `cancelled` 触发 → `takeUntil` 掐断上游模型流，而 cache 的缓冲对后续订阅者依然可用。**重放与取消，两全**。

我把这个修复部署到生产环境做了真实负载验证：流式排查进行到工具轮时直接关掉浏览器标签页（不走任何停止接口，让客户端凭空消失）——断开后日志**零后续活动**：没有新的工具轮、没有续流、没有后台生成。对比修复前的 3 分钟空烧，取消传导精确生效。

## 应用层方案：协作取消标志

框架层的修复解决的是"dispose 能传导"；但生产上还有一种场景它覆盖不了：**用户点了"停止"，但客户端连接还在**（或者你想在服务端主动停掉某次运行）。这需要应用层的协作取消：

```
REST 端点(chat_stop)
   → 置 per-run 的 volatile 标志
   → 模型循环在每个 chunk 增量、每个工具轮边界检查标志
   → 命中：停掉当前模型订阅，已生成的思考/正文按阶段性结果落库收尾
```

三个设计要点：

1. **标志是 per-run 的**（volatile boolean），不是全局开关——不同用户的运行互不影响；
2. **检查点选在 chunk 边界和工具轮边界**——粒度足够细（停止响应 <1 秒），又不至于在流处理内部制造竞态；
3. **取消要"优雅收尾"而非"报错清场"**：已生成的思考、阶段性结论正常落库，附一句系统提示说明中止原因——用户发"继续"可以从完整状态续查。点停止是用户的权利，不是用户的错误。

## 组合：两道防线各管一段

| 场景 | 生效机制 |
|---|---|
| 用户直接关页面/网络断开 | 框架层：dispose 传导（#1621 修复后） |
| 用户点"停止"按钮 / 服务端主动终止 | 应用层：协作取消标志 |

两套机制在同一次流式运行里共存验证过：断连场景由框架层取消传导接住，主动停止场景由协作标志优雅收尾——互不干扰，**组合后所有已知的"停不下来"场景都有解**。

## 给同路人的清单

如果你的架构也是"响应式流 + 外部模型调用"，检查四件事：

1. 中间算子有没有 `cache()` / `replay()` / 共享订阅——它们的取消语义和直觉相反；
2. 断连实测：断开客户端后，模型/下游资源侧有没有后续活动（看日志，不要看接口返回）；
3. 有没有公开的"停止一次运行"入口——没有的话，应用层协作标志是最小可行方案；
4. 取消后的收尾是"清场报错"还是"阶段性结果保留"——用户体感天差地别。

## 现状

框架层修复（[#1621](https://github.com/google/adk-java/pull/1621)，对应我报的 [#1618](https://github.com/google/adk-java/issues/1618)）已完成生产验证并进入评审收尾；应用层协作取消在我的智能体工作台稳定运行。上游公开取消 API 的讨论（#1341）也在推进——框架原生方案落地后，应用层标志可以退化为纯业务控制，但那是后话了。
