> 10 月 4 日，我在自己的 AI 排查智能体项目里踩到第一个 ADK Java 框架层的问题；10 月 14 日，我写的修复随 google/adk-java v1.12.0 正式发版。十天，5 个 issue、2 个 PR（1 个已合并、1 个评审中）、1 个 Feature Request、还有一次以"报告者"身份完成的生产验证。这篇把整个过程、每个判断点和踩到的流程细节完整记录下来。

## 背景：为什么会在框架层踩坑

我的智能体工作台架构是 Spring AI 2.0（管模型交互与工具注册）+ Google ADK（管多智能体编排）双框架桥接：ADK 官方提供了 Spring AI 桥（`contrib/spring-ai`），但生产用下来发现这个桥相对年轻——中文场景的问题一个接一个。official 桥不管的部分我只能自己写桥接层补，补的过程中积累了对官方实现的深入理解，这成了后来一切上游贡献的基础。

## 第一个 Issue：中文回复"消失"之谜

**现象**很诡异：排查智能体的回复当时看得到，翻历史却没了，下一轮对话模型不知道自己说过什么——多轮上下文静默丢失，极像会话存储坏了。

**定位**花了点功夫：ADK 只持久化 final 事件（partial 事件只流给前端），而官方桥判断"一个流式 chunk 是不是最终回复"用的是 **ASCII 标点启发式**（`.!?` + 换行）。中文回复以`。！？`结尾——ASCII 集合不认识——整场回复所有 chunk 都被判为"未完成"，一个 final 都不存在，自然什么都不落库。

更隐蔽的是反向问题：英文长回答中间某个 chunk 恰好以句号结尾，会提前触发"最终"，把半截话当完整回复落库。

**双版本探针**：我先怀疑是某版引入的回归，于是拿 1.9.0 和 1.11.0（当时最新）跑了同样的输入——输出逐字节一致。这说明不是回归，是这个启发式从写出来的第一天就注定失败。这个结论直接影响了 issue 的质量：官方看到的不是"某个版本坏了"，而是"设计本身有问题"。

## 第二个 Issue：被静默丢弃的 schema

排查智能体里有带枚举参数的工具，模型总是传错值。追到官方桥的 `ToolConverter.convertSchemaToSpringAi`：它只映射 `type/properties/description/required` 四个字段——**`enum` 和 `items` 被静默丢掉**。

后果有两层：枚举参数退化成自由文本，模型开始"自由发挥"；更阴险的是整个过程零报错零日志，生成的 schema "看着很完整"，所有排查方向都会被误导到提示词或模型能力上。

同样双版本探针实锤，提交 **#1609**。

## 四十八小时：从提交到双认领

两个 issue 提交（10-04），10-05 早上维护者 hirematha 就 self-assign 并标了 Bug。这个速度超出我预期，事后想原因：**报告质量决定了 triage 速度**——每个 issue 都附了最小复现、双版本对照输出、以及"为什么是设计问题而不是回归"的判断。

我随即在 issue 下发了方向对齐评论：修复有两条路（最小补丁加标点 vs 流完成信号根治），我倾向后者，但先问维护者的意见。**先对齐方向再动手**，这一步让后面 PR 的评审顺畅得多。

## 第一个 PR：一周内合并发版

方向确认后我在 fork 里建分支实现。修复本身不大——官方代码里 `StreamingResponseAggregator` 早就存在（Gemini 桥在用同样的模式），只是 spring-ai 桥从没接线。我的 PR 本质上是**把官方自己的零件装回该在的位置**：

1. 流式 chunk 一律标 partial、原样转发（不再逐 chunk 猜测）；
2. 流完成时由聚合器发出唯一一个 final 事件（全量文本 + 累计工具调用 + usage）；
3. 旧的标点判定函数保留并标注废弃。

评审（wikaaaaa）给了 "correct and safe" 的定调，两轮共 9 条意见——Javadoc 补关键字清单、测试要走端到端序列化路径、对象数组递归用例、unchecked 警告……全是打磨级的。每条当天消化，10-12 合并，**10-14 随 v1.12.0 发版，release notes 具名条目**。

两个流程细节值得记录：

- **仓库要求 PR 单 commit**。我开发时每次修改都 amend + force-push，保持历史干净；PR 开出之后的修改则改为正常追加——改写已公开历史会让 reviewer 的 diff 突变；
- **回复 review 别沉默**。我第一轮只改代码没回评论，第二轮 review 后补了逐条回复 + 一句"Apologies for the silence"。reviewer 提意见是投入，回应是基本的协作礼仪。

## 第三个 Issue：反编译出来的 Feature Request

用探针验证修复时顺手发现：官方桥对思考模型（DeepSeek-R1/GLM 这类）的 `reasoning_content` **完全不处理**——反编译 1.11.0 的四个核心桥类，reasoning 相关引用为零。思考模型的推理流被静默丢弃：不透传、不落库、无警告。

这次我走 Feature Request（**#1616**）：Spring AI 2.0 明明把 reasoning 放在了 metadata 里等桥来取，桥却不读——需求真实存在，解法清晰（流式时作为 thought part 透出）。提交后进了团队评审。这一条和后面要写的思考守护篇是同一条产品线：让思考可见，让思考可控。

## 第四个 Issue：断开连接后，模型还在烧钱

这个是架构级的。现象：SSE 客户端断开后，模型流**没有被取消**，在后台继续生成——一次事故里后台空烧了 3 分多钟，纯 token 浪费。更严重的是框架没有任何公开的"停止一次运行"的 API。

根因在 `BaseLlmFlow:530`：每步事件流被 `.cache()` 了，而 RxJava 的 cache 语义是"所有订阅者全部取消才断开上游"——框架内部还挂着订阅者，用户侧的 dispose 永远传不到模型流。

这个 issue 提交后发生了我觉得最有意思的事：**另一位贡献者 sangkyoonnam 独立复现了我的发现，直接开了修复 PR（#1621），并问我要不要接手**。我的判断是让给他（他 9 个测试已完成 8 个，接手等于夺走别人近完成的贡献），自己转为验证者角色——用生产环境跑了真实断连测试：关掉浏览器标签页后，日志零后续活动，取消精确传导。验证报告被作者引用进了 PR 评审材料，现在 #1621 已有两个 approve。

## 复盘：这次经历里做对了什么

1. **报告质量 > 数量**：每个 issue 都是"现象 + 复现 + 根因 + 双版本对照"，维护者拿到手就能行动。triage 速度是对报告质量的直接反馈；
2. **先对齐方向再写代码**：方向评论让我第一个 PR 零返工；
3. **反编译和 sources jar 是一手证据**："你们已有 90% 的零件"（官方聚合器没人调用）是最强的 PR 论据；
4. **知道什么时候让**：让出 #1621 的实现权、接下验证者角色，对社区和个人都是更优解；
5. **产线是后盾**：所有 issue 都来自真实生产使用，"我的生产环境验证过"这句话在评审里的分量，比任何测试都重。
