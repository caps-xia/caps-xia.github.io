> 这是一段网约车分销业务的线上复盘。现象是司机接单后订单状态推送频繁超时，最后定位到数据库死锁——根因是"事务内发起 RPC"这个非常常见的写法。整理这篇时我已经离开了那个项目，但这个案例每讲一次都觉得值得再讲一次。

## 现象

司机接单后，系统要把订单状态推送到分销侧，但推送调用频繁超时。奇怪的是：推送逻辑本身并不重——一次简单的状态同步，为什么会慢？

## 排查

顺着调用链往下查，发现慢的不是推送本身，而是推送到达分销侧之后：**分销侧更新订单状态的那条 SQL 执行极慢**，进一步确认是发生了数据库死锁。

死锁日志把两个事务的互等关系摆了出来，图景一下子清晰了。

## 根因：事务内的 RPC 调用

出问题的代码结构大致是这样的：

```text
司机接单（事务 A，传播机制 REQUIRED）
1. 锁定记录 R1
2. 尝试更新 R1 的手机号
3. 其中通过 RPC 调用服务 B（无事务上下文）更新 R1 的状态
4. 提交
```

时序拆开看：

1. **事务 A 启动并锁定记录 R1**——这是行锁，本身没问题；
2. **事务 A 在未提交的状态下，通过 HTTP 调用了服务 B**——问题就出在这里：网络调用把"持锁时间"从毫秒级拉长到了秒级；
3. **服务 B 尝试更新同一条记录 R1**——它没有自己的事务边界，但它的 UPDATE 依然要拿 R1 的行锁；
4. 此时的 R1 行锁还攥在事务 A 手里，服务 B 被阻塞，直到事务 A 提交或回滚。A 又在等 B 的 RPC 返回——**互相等待，死锁（或超时）就此成型**。

本质是一句话：**事务的边界里混进了远程调用，锁的持有时间被网络不可控地放大了。**

## 修复

方向就是切断"锁与网络"的耦合：

1. **缩小事务边界**：RPC 调用移出事务 A（或改为异步消息），让"锁记录"和"调远程"不再同时发生；
2. **跨服务一致性改走最终一致**：这类跨服务状态同步，用消息队列解耦，或采用 Saga 式的补偿设计，而不是指望把两个服务塞进一个"事实上不存在"的分布式事务里。

## 复盘与预防

- 代码评审时看到 **`@Transactional` 方法里有 HTTP/RPC 调用就该警惕**——它不只是慢，还可能把行锁变成分布式故障点；
- 同一段时期分销侧流量激增还引发了整体 SQL 变慢，配套做了基于 Redis 有序列表的**滑动窗口限流**：按分钟窗口清理过期记录、校验当前计数是否超阈值，未超则放行并计数 +1。限流保护的是数据库这个最后的瓶颈资源。

死锁四要素里最经典的就是"持有并等待"——这次它穿上了微服务的外衣，但内核没变。
