> 数据割接脚本要迁 4457 万行数据，同事问我线程开多少。网上说法五花八门，我的回答是：别查资料了，直接测——反正割接初期生产环境还没人用，周末晚上跑一轮实验，一小时出真数。

## 实验设计

控制变量，只动线程数：

- **数据量**：44,572,331 行，按每 100 万行一个文件拆分，每 1000 条一批处理，涉及 3 张表的插入；
- **机器**：物理 CPU 2 颗 × 6 核，支持超线程，共 **24 逻辑核**；内存 125G；
- **环境**：割接初期、周末晚间，生产逻辑流量近乎为零——排除外界干扰。

## 实测结果

| 线程数 | 耗时 |
|---|---|
| 12 | 301s |
| 24 | 271s |
| 25 | **264s** |
| 48 | 261s |
| 120 | 271s |
| 240 | 268s |

## 三个观察

1. **24 → 25 有个台阶**：恰好跨过逻辑核数，收益陡增——不多解释，看下一个观察；
2. **48 线程反而最快**：这是 IO 密集型任务的典型曲线——线程在等数据库响应时会阻塞，适度超配（2× 逻辑核）能让 CPU 在等待间隙做别的活；
3. **120 / 240 开始回退**：线程数继续往上加，上下文切换和连接争用的开销吃掉了并发收益，甚至比 25 线程还慢。

## 结论与实践

- **这台 24 逻辑核的机器上，48 线程（2× 逻辑核）是最优解**；
- 通用公式只值得当先验：IO 密集 ≈ 2× 核数起步，CPU 密集 ≈ 核数 + 1——但**真正的答案永远来自实测**；
- 割接类任务的额外好处：环境可控、可重复、代价低，是做容量实验的完美场景。与其背八股文的线程数公式，不如在你的真实链路上跑一遍像这样的对照实验。
