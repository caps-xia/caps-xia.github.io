> 前一篇写了线程数怎么定，这篇是当时几个平台割接踩过的坑合集——天眼割接 OOM、Redis 占用、话单连接超时。单个看都是小坑，串起来就是一份"割接前检查清单"。

## 坑 1：本地跑得通，生产 OOM

**现象**：割接脚本在本地 IDEA 跑完 200 多万行没问题，打包上生产跑到 800 万时 OOM。

**排查**：对比两端 JVM 参数——本地 `-Xmx2048m`（IDEA 默认模板），生产 `-Xmx2g`。看似一致，但**数据量本身在增长**：跑到 800 万行时脚本内的累积结构已经超出 2G 堆的预算。

**当时的处理**：生产内存充裕、时间紧急，直接把堆扩到 8G（堆 ×4、非堆 ×2、栈 ×2）先跑完。

**正确的姿势（事后补课）**：扩参数只是止血。根因是脚本内的**累积结构没有按批释放**——流式处理（读一批、写一批、丢一批）才是割接脚本的正确形态，堆大小只是把问题推迟。

## 坑 2：割接会"打爆"共享的 Redis

割接高峰期 Redis 内存占用异常飙升，殃及同实例的其他业务。

教训：**割接的写入速率要主动限流**，尤其是共享缓存/存储——你的"尽快跑完"不该由别人的业务买单。割接窗口申请时，资源隔离（独立实例或至少独立配额）要写进方案。

## 坑 3：话单同步频繁 ConnectionTimeout

割接后的话单拉取频繁连接超时。

排查指向**连接池容量与超时参数**的配置缺口——批量脚本与在线业务的连接画像完全不同（长事务、大结果集、高并发短连接），混用同一套池配置必然打架。

## 沉淀：割接前检查清单

跑过四个平台的割接之后，这份清单值得留在任何一次数据迁移前过一遍：

1. **堆与数据量匹配**：脚本内存形态是流式还是累积式？流式则堆无需随数据量线性放大；
2. **共享资源限流**：Redis/DB 是共享的话，写入速率有没有上限？别人知不知道你的窗口？
3. **线程数实测**：按 2× 逻辑核起步做一轮对照实验（见前一篇），不拍脑袋；
4. **连接池按画像配置**：批量任务单独的池参数（超时、容量、验证查询）；
5. **校验方案先行**：割完怎么证明"割对了"——行数、抽样字段比对、checksum，三选一不够就组合；
6. **回滚预案**：割接失败的退路是什么？"重跑一遍"和"回滚到快照"是两种完全不同的预案成本。

## 复盘

数据割接是后端少有的"低频但高压"任务：平时用不上，用上时不容错。**坑的价值不在坑本身，在把它们变成清单的能力**——每个平台踩一遍是学费，清单让学费只交一次。
